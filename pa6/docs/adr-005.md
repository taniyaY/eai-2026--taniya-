# ADR-005 — Sequential checkout saga with durable idempotency

**Status:** accepted  
**Date:** 2026-11-02

## Context

Checkout is one business decision spanning four services that do not share a database transaction. Payment must be authorized before stock is reserved, and shipping and notification must not start until those earlier steps succeed. A timeout is different from a business rejection: the caller may not know whether a remote operation completed, so the orchestrator must bound every request and record what it observed.

The canonical order deliberately contains neither a payment amount nor a notification recipient. The amount therefore has to be derived from each item's decimal-string price and quantity without floating-point rounding, while the recipient comes from `customer.email`. The published API also needs to state a real upper bound for `items`; the canonical schema itself does not supply one.

## Decision

The contract is committed separately before the orchestrator implementation. `POST /checkout` accepts the canonical order unchanged, requires `Idempotency-Key`, and documents success, validation, conflict, business-failure and timeout responses. The contract bounds `items` to 50, and the implementation enforces the same limit.

The orchestrator in `orchestrator/src/server.ts` executes payment authorization, inventory reservation, shipping creation and notification sequentially. It calculates the payment amount in integer cents and formats it once as a two-decimal string. Each downstream call has `REQUEST_TIMEOUT_MS`, and each attempt appends a trace item with start/end timestamps and duration. A timeout maps to HTTP 504 and code `timeout`; a downstream business failure maps to 422 and preserves the mock's machine code.

Only payment and inventory have compensating endpoints. When a later step fails, completed steps are visited in reverse order: inventory is released before payment is refunded. Shipping and notification are not compensated because their mock contracts expose no reverse operation. If any compensation fails, the final result is HTTP 422 with `compensation_failed`. The response and both durable JSON stores are updated with the final outcome.

The idempotency store is written to `/data/idempotency-store.json` before the first remote call. A matching key and payload after completion returns the stored HTTP status and body without repeating work. A different payload returns 409 `idempotency_payload_mismatch`; a matching request that arrives while the first is running returns 409 `idempotency_conflict`. Saga traces are persisted separately to `/data/saga-store.json`, and both files are bind-mounted so they survive container recreation.

## Alternatives considered

Parallel downstream calls would reduce the happy-path latency, but would violate the business ordering and make it unclear which actions had completed when one failed. Strict sequencing makes the trace and compensation order deterministic.

Adding compensation endpoints to shipping and notification would make the saga look more like a database rollback, but it would invent guarantees the downstream systems do not provide. A sent notification cannot be unsent, and a shipment may already have triggered an external carrier. The implementation therefore compensates only actions with real reverse operations and reports the partial outcome honestly.

A process-centric orchestrator was chosen over PA5-style event choreography. Checkout moves money and stock and needs one visible owner for ordering, compensation and the final answer. Choreography remains appropriate for independent reactions such as analytics or notifications that do not gate the transaction.

## Consequences

The caller gets a deterministic final response, a trace in actual execution order, and safe replay after a completed request. The trade-off is that the HTTP request remains open while the four calls run, and the orchestrator is a critical component that must be monitored. Adding a fifth step requires a new contract decision, an explicit position in the sequence, a timeout, and (if available) a compensation rule.

The JSON stores are durable across container restarts but are not a transactional database. If the process is killed mid-saga, the idempotency record can remain `in_progress`; a retry then receives a conflict rather than silently starting a second charge. Two different idempotency keys for the same order can also race because the key, not the order ID, is the uniqueness boundary. A production implementation would need recovery for abandoned sagas and a transactional store with concurrency control.
