# ADR-004 — Per-consumer delayed retries and durable notification identity

**Status:** accepted  
**Date:** 2026-10-26

## Context

The order publisher broadcasts a canonical order to independent payment, inventory and notification consumers. Failed downstream work should not prevent other departments from receiving their copies. RabbitMQ may redeliver, and malformed inputs will never become valid on retry.

## Decision

Use the provided durable fanout exchange for original orders, and the direct return exchange for one-consumer-only retries. Each consumer declares durable invalid and DLQ fanout channels during startup. Unparseable JSON or orders without required identity are permanently invalid and are acknowledged only after routing the original payload to the invalid channel. Temporary simulated outages use a one-second TTL retry queue and at most three attempts before the DLQ, with an originQueue header for selective replay.

The HTTP producer assigns a UUID as a custom AMQP `headers.correlationId` while leaving the strict canonical order body unchanged. Results use the same header, allowing correlation across independent subscriptions. The notification consumer persists correlation IDs at `/data/processed-ids.json` to suppress duplicate notification log entries after service restarts. DLQ replay removes RabbitMQ retry-history headers and sends messages to their originating queues via `orders.return.exchange`.

## Alternatives considered

A retry through the original fanout would force healthy services to repeat already completed work. Immediate requeue would create an uncontrolled busy loop. A memory-only processed-ID set would be lost after restart, allowing duplicate notifications. One shared error queue would confuse invalid producer payloads with valid messages that exhausted temporary retries.

## Consequences

The topology limits retry work to its failing recipient while preserving messages for operational inspection. A failed provider can still leave an order partly completed after the retry budget expires; this assignment does not implement compensation. File-based notification deduplication works for one process but is not fully crash-atomic and must become a transactional store before scaling to multiple instances. DLQ monitoring and human replay procedures are necessary in production.
