# ADR-002 — Aggregating split order results safely

**Status:** accepted  
**Date:** 2026-10-05

## Context

Once an order is split, its items no longer travel together. A physical item,
a digital item, and a subscription item may finish at different times and in a
different order. The aggregator therefore needs a reliable way to reconstruct
one logical order from independent result messages.

RabbitMQ may also redeliver a message, and a worker may fail to answer at all.
The design must avoid double-counting duplicates and must eventually produce a
useful result instead of waiting forever.

## Decision

Every split item carries four pieces of coordination data: `orderId`,
`correlationId`, `itemIndex`, and `totalItems`. The router sets
`correlationId` to the order id so all messages from one order share the same
correlation value.

The aggregator keeps one in-memory record per `orderId`. Inside that record,
results are stored in a dictionary keyed by `itemIndex`. This means receiving
the same item twice replaces the existing value instead of increasing the
number of received items.

The timeout is an idle timeout of 5 seconds. The timestamp is refreshed whenever
a valid result arrives. A watcher thread periodically finds orders that have
made no progress for at least five seconds. Those orders are emitted with
`status: "partial"`. The completion message includes every result received so
far and a `missingItemIndexes` list calculated from the expected index range.
For a fully completed order, the same field is present as an empty list.

## Alternatives considered

A fixed deadline from the first result was considered. It is simpler, but it can
cut off a large order even while new results are still arriving. An idle timeout
better distinguishes a slow but progressing order from one that has stopped
making progress.

A list was considered for collected results. It was rejected because duplicate
delivery would create two entries for the same item and could make the
aggregator believe the order was complete too early. Keying results by
`itemIndex` avoids that problem naturally.

Persisting the aggregation state in Redis or a database would make recovery
stronger, but it would add another service and persistence logic that are beyond
the needs of this assignment.

## Consequences

The design handles concurrent orders independently, accepts out-of-order worker
responses, and makes duplicate item results harmless. Callers also receive the
exact missing indexes when a timeout occurs rather than only a generic failure.

The trade-off is that the aggregation state and the set of already-finished
orders live only in memory. Restarting the aggregator can lose unfinished state
and its duplicate history. A production version should move that state to a
durable store and define a retention policy for completed order identifiers.
