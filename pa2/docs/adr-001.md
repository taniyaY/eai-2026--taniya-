ADR-001 — Reliable Message Delivery Using RabbitMQ and amqplib

Status: accepted
Date: 2026-09-20

## Context

Our order pipeline talks to a warehouse service that is often slow or down for maintenance. We can’t just block on a direct HTTP call because if the warehouse is down for 10 minutes, our client orders shouldn’t fail. So, we put RabbitMQ in the middle as a buffer. However, simply adding a broker does not automatically make the system reliable, and each part of the pipeline had a failure mode that showed up during testing:

* If the queue isn’t marked as durable, running docker restart pa2-rabbitmq removes the queue and its messages. Even if the queue survives because durable: true is set, messages without persistent: true are not guaranteed to survive a broker restart because RabbitMQ treats them as non-persistent. In Demo C, publishing 5 messages with X-Publish-Mode: fire-and-forget and killing the broker with docker kill pa2-rabbitmq caused messages to disappear even though the client had already received a 202 response.
* By default, channel.publish() puts the message into the client-side write buffer and returns a boolean indicating backpressure. If we return 202 immediately without waiting for a publisher confirmation, the client thinks the order has been accepted by RabbitMQ even though the broker may not have received or persisted it yet.
* With auto-ack (noAck: true), RabbitMQ considers the message handled as soon as it delivers it to the consumer. If the consumer container crashes while writing to received.jsonl, that message is lost.
* Correlation IDs also need to be traceable end-to-end. If a client sends an X-Correlation-Id header, or if we generate a UUID, it needs to follow the message from HTTP to the AMQP message property, then to the consumer log and received.jsonl. If it is only recorded in one place or stored in the wrong field, we lose the ability to trace the message through the pipeline.

## Decision

We implemented the four required parts in producer.ts and consumer.ts:

1. In connectProducerChannel and connectConsumerChannel, we declare the queue pa2.orders with channel.assertQueue(queueName, { durable: true }). Both sides declare it identically so whichever side starts first creates the durable queue.
2. For publisher confirms, connectProducerChannel uses connection.createConfirmChannel(). In publishMessage:
    * In the default confirmed mode, we set { persistent: true, correlationId: options.correlationId } and wrap channel.publish() in a Promise that resolves only when the broker’s confirmation callback fires. This means handlePublish only responds with 202 after RabbitMQ confirms that it accepted the message.
    * In fire-and-forget mode, used for Demo C, we publish without persistent: true and resolve immediately without waiting for a publisher confirmation.
3. In connectConsumerChannel, we added channel.prefetch(10) so RabbitMQ does not send more than 10 unacknowledged messages to the consumer at a time. In handleMessage, we extract msg.properties.correlationId, build the JSON object with receivedAt, write it to data/received.jsonl using appendFileSync, log it, and only then call channel.ack(msg). The manual acknowledgement therefore happens after the write completes.
4. For the correlation ID, producer.ts validates the incoming header against the regex ^[A-Za-z0-9._-]{1,128}$ or generates one using randomUUID(). It is passed in the AMQP message metadata as msg.properties.correlationId rather than being added to the payload body. The consumer reads msg.properties.correlationId, logs it, and saves it into received.jsonl.

## Alternatives considered

* Acknowledging before writing to received.jsonl: We rejected this because if appendFileSync fails or the consumer dies between the acknowledgement and the write, RabbitMQ considers the message handled and removes it from the queue. This can cause message loss. Moving the acknowledgement after the write provides at-least-once delivery for the consumer processing step.
* Relying on the channel.publish() return value: The boolean returned by publish() only indicates whether the internal write buffer is full and is useful for backpressure. It does not confirm that RabbitMQ received or persisted the message. A broker failure immediately afterward could still cause the message to be lost.
* Auto-ack with low prefetch: Although this is slightly simpler, auto-ack removes the message from RabbitMQ before processing is complete. Any consumer failure after delivery but before writing the message can therefore result in message loss.
* Putting correlationId inside the JSON message body: We rejected this because it would require parsing and modifying client JSON payloads and would not work consistently if payloads were raw buffers or non-JSON data. AMQP message properties are designed for transport metadata such as correlation IDs.
* Using the default guest/guest credentials: RabbitMQ restricts the default guest user to loopback connections. Therefore, using it for host-to-container management access would not work as required. We used the configured eai:eai-pa2 credentials instead.

## Consequences

* Orders published in the default confirmed mode are more resilient to broker restarts when the queue is durable and messages are persistent. When the consumer is stopped, messages remain in the queue and can be processed after the consumer restarts, as demonstrated in Demo B.
* Write latency is higher on POST /publish because the application waits for a broker confirmation instead of immediately returning after the local publish call.
* If the consumer crashes after appendFileSync completes but before channel.ack() executes, RabbitMQ can redeliver the message when the consumer reconnects. This provides at-least-once delivery but can result in duplicates. Downstream processing therefore needs to handle duplicate messages, for example by using the correlationId.
* If the consumer remains down for a long time while messages continue arriving, the queue depth will grow and consume broker disk space. If disk space becomes critically low, RabbitMQ’s disk alarms can block producers from publishing new messages.
