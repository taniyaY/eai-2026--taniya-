# ADR-003 — Canonical translation with live pricing and safe filtering

**Status:** accepted  
**Date:** 2026-10-13

## Context

PA4 receives the same logical order from three systems that disagree on representation. The web source is nested JSON, the mobile source is flat JSON with an epoch timestamp, numeric status/currency codes and a comma-separated address, and the B2B source is XML encoded as windows-1257. The B2B file must therefore be decoded from bytes before XML parsing; treating it as UTF-8 corrupts Latvian characters without necessarily producing a parsing error.

Product identifiers also differ by source: web already sends `PROD-XXX`, mobile sends only the numeric part, and B2B sends `SKU-PROD-XXX`. None of the sources owns a trustworthy current price, so the translator must call the pricing API. All three sources also contain payment information that is deliberately absent from the canonical schema and must not be propagated.

The pricing dependency can fail. A product can return 404, while the service can return another error or be unreachable. The assignment requires the transformation to report those problems in warnings instead of throwing away the whole order.

## Decision

I kept the three public translator functions separate at the source boundary, but made them share the normalization and enrichment helpers.

`normalizeProductId` converts each source-specific identifier to the pricing service's `PROD-XXX` form. `enrichFromPricing` calls the supplied `pricingBaseUrl` with the required `X-API-Key`, and `enrichItems` converts successful responses into canonical items. Prices are formatted with `toFixed(2)`, so a value such as `4.5` becomes the canonical decimal string `"4.50"` rather than a floating-point JSON number.

A 404 becomes an `UNKNOWN_PRODUCT` warning. Other HTTP failures and network failures become `PRICING_API_ERROR` warnings. The affected line item is omitted, while other line items continue through the transformation. If every item fails enrichment, the function returns `order: null` because the canonical schema requires at least one item.

The mobile timestamp is converted from epoch seconds to ISO-8601 UTC, its currency and status codes are mapped explicitly, and its address string is split into the four canonical address fields. The B2B input is read as raw bytes and decoded with `TextDecoder("windows-1257")` before parsing. B2B line items are normalized to an array so the same code works for one or many items, and unrecognized XML elements are ignored.

Payment data is filtered by construction. Each translator creates a new canonical object field by field rather than copying a source object and deleting known sensitive keys. As a result, web payment details, mobile PAN/expiry fields, and B2B payment/IBAN/BIC fields never enter the returned canonical object.

## Alternatives considered

I considered failing the entire order when one product could not be priced. That is simpler, but it discards useful results from healthy line items and conflicts with the assignment's warning-based partial-result behavior.

I also considered using the product name returned by the pricing API. I kept the source product name because the pricing service is authoritative for price, currency and tax rate, while the source order is still the statement of what the customer ordered. The API's product name is therefore not required to construct the canonical order.

For filtering, another option was to clone the source and remove payment-related fields. I rejected that denylist approach because a new sensitive field could leak automatically. Constructing the canonical object from an allowlist is safer.

Caching pricing responses could improve throughput, but it would introduce a staleness policy and could make a runtime price change invisible. PA4 explicitly tests that changes in the pricing catalog are reflected immediately, so every item lookup goes to the pricing API.

## Consequences

The three translators now produce one stable canonical shape and can tolerate extra B2B elements because only known fields are read. Sensitive payment data is excluded by default, and pricing failures are visible to the caller through structured warnings instead of crashing the whole transformation.

The main cost is a synchronous network request for every item, so pricing latency directly affects translation latency. There is also deliberately duplicated source-specific mapping code because each source has a different boundary contract; keeping that mapping explicit makes the differences easier to review.

The implementation depends on the fixed canonical schema. If that schema gains a new required field, every translator must be updated together. If a fourth source introduces a new product-id convention, a new normalization rule must be added. A production system would likely add schema-version governance, bounded caching where acceptable, and stronger monitoring around pricing failures.
